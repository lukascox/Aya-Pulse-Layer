# Discrete fan modes — first on-device confirmation (2026-07-31)

Pulled `pulse-for-aya` session logs from the test that confirmed discrete
fan-mode control (Silent/Smart/Sport over the `com_set_performance_fan`
AIDL command) working live, and that answered the open question about
whether gamewindow pushes its state callback unsolicited. Full writeup:
`research/pulse-for-aya/README.md`, "Discrete fan mode implementation

## "clean session end: NO — crash suspected" is a false positive, provably

Both groups in `pull-00-20/` are flagged. Neither is a crash, and this time
it does not rest on inference: the two sessions report **different build
stamps** — `…001703` is `built 2026-07-30 18:29:13`, `…001729` is
`built 2026-07-30 23:48:10`. A crash cannot change the build, so the
"unclean end" at 00:17:28 was `adb install -r` replacing the app, one second
before the next session starts. (The per-build timestamp added 2026-07-28
exists for exactly this and paid for itself here.) The flag is a
missing-STOP-marker heuristic and reads identically for an install, a
reconnect, and a real crash.

## Why the dmesg and logcat files were dropped

- **`_logcat.log`** (43 KB, both groups) — the two files were **byte-identical**
  (same ring-buffer dump). Its 14 crash-keyword hits are all timestamped
  00:16:51–00:16:56, i.e. **before** either session started (00:17:02), in
  `init` / `nvkeeper` / `qcrosvm` (a Rust panic in Qualcomm's VM manager),
  plus one `01-04` entry from a pre-NTP-sync boot. System/boot noise sitting
  in the ring buffer, nothing to do with PULSE.
- **`_dmesg.log`** (287 KB + 111 KB) — zero crash hits in the main session;
  the two hits in the short one are benign lines that merely contain the
  words (`gh_panic_notifier … assigned reserved memory node` is a
  registration message, `sde_dbg_init … panic:1, dump:2` is a debug config
  line).

## What these logs do NOT contain

**The decisive fan evidence is not here.** `pulse_daemon.sh`'s detached
logcat is deliberately filtered to crash tags only
(`AndroidRuntime:E libc:F DEBUG:F …`) to avoid ring-buffer overflow on long
sessions, so **`PulseFan` lines never reach a pulled log** — they were
captured live in a terminal (`adb logcat -s PulseFan:D`). The load-bearing
excerpt, preserved here because it exists nowhere else in the repo:

```
00:18:32 AIDL callback …   00:18:33 arbiter=None … managed=1   (Silent)
00:18:37 AIDL callback …   00:18:38 arbiter=None … managed=5   (Sport)
00:18:41 AIDL callback …   00:18:41 arbiter=None … managed=4   (Smart)
── user then changed the fan in native AyaSettings ──
00:19:13 AIDL callback …   (managed stays 4 — so not our send)
00:19:16 arbiter=SetVendorMode(mode=4)
00:19:16 fan_mode drifted, want=4 — re-applying
00:19:17 arbiter=None
```

First phase: every callback pairs with a `managed=` change — those are
echoes of our own sends. Second phase: `managed` never changes yet
callbacks keep arriving, so they cannot be ours. That is the proof that
gamewindow pushes unsolicited, which makes the callback a true drift
detector rather than just an acknowledgement. Correlating the `_cap_poll`
duty/RPM columns against those same mode changes is what showed the modes
are indistinguishable at idle (all converge on ~30–32% duty, ~2750 RPM).
